## Findings

### R1 — P1: NAT compatibility guard rejects Native VLAN

`src/commands.rs`, `plan`, around line 356: `p.starts_with("nat")` also matches normalized `nativevlan`. A valid switch Native VLAN checkpoint is rejected before reaching its typed switch handler. This breaks an existing supported command family and the repository test `supported_families_have_scoped_commands` at `tests/commands.rs:213`.

Reproduce with `cargo test --locked --test commands supported_families_have_scoped_commands`: the candidate reports `Native VLAN: This router command family requires a separately implemented and evidenced switch-specific workflow`. Use explicit NAT property identities instead of this prefix. Keep the existing test and add a direct Native VLAN versus NAT role compatibility table so future family aliases cannot collide.

### R2 — P2: legacy gateway mapping bypasses typed prerequisites

`src/cisco/mapping.rs`, `request`, has no Default Gateway/Gateway arm; `src/commands.rs`, `plan`, around line 453, retains an unconditional legacy `ip default-gateway` branch. The newly added prerequisite guard applies only to router profiles. A Switch checkpoint with `assessment:device-model=3560`, expected gateway `192.0.2.1`, and `commands:parameter:ip_routing=enabled` returns `supported=true` and a copyable gateway command. It also succeeds without the management address/mask required by `switch.default_gateway`.

This is misleading command readiness: the typed library rejects the same incomplete or incompatible scenario, while assessment-generated suggestions bypass it. Cisco documents the [3560 default gateway workflow for disabled IP routing](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst3560/software/release/15-0_1_se/configuration/guide/scg3560/swiprout.html). Map switch gateway checkpoints through that typed family and reject enabled, missing, or contradictory routing evidence. Test `Gateway` and `Default Gateway` aliases on 2960, 3560, router, unknown profile, and GUI endpoint, with disabled/enabled/missing/conflicting evidence and subnet-host checks.

### R3 — P2: contradictory model evidence silently becomes a generic router

`src/cisco/mapping.rs:4`, `profile`: multiple distinct `assessment:device-model=` values cause fallback to `device_type`. A single Router checkpoint containing both `assessment:device-model=2960` and `assessment:device-model=2911`, expected static route `10.0.0.0 255.0.0.0 192.0.2.1`, becomes `GenericRouter`; `commands::generate` returns `supported=true`, and `device_script` emits the route. The group-level mixed-model check sees only the already collapsed profile and cannot detect this ambiguity.

Preserve ambiguity as a separate rejection condition through individual generation and batch copying. Regression tests should cover contradictory models inside one checkpoint, model/kind contradictions, and contradictions spread across checkpoints. Repeated identical evidence should remain usable; genuinely unknown models should remain visibly unknown rather than falsely proven compatible.

### R4 — P2: equivalent nonzero OSPF areas compare unequal

`src/inspector.rs:725`, `semantic_equal`: only `0.0.0.0` is normalized to decimal `0`. An expected value `20 10.0.0.0 0.255.255.255 2` compared with uniquely owned running configuration `router ospf 20` / ` network 10.0.0.0 0.255.255.255 area 0.0.0.2` returns `Failed`. The independent probe reproduced that status on both reviewed candidates.

Cisco's [IOS OSPF network area reference](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/iproute_ospf/command/iro-cr-book/ospf-i1.html) permits decimal or IP-address area notation. Compare their complete 32-bit numeric identities. Regressions should include `2` versus `0.0.0.2`, `16909060` versus `1.2.3.4`, both backbone spellings, different areas, malformed values, and distinct process IDs. The coordinator reports implementing this fix; no fixed commit was available in the tested HEAD.

### R5 — P2: registry defaults do not form valid example requests

An independent probe iterated `cisco::registry()`, supplied every required field's `example`, and used Router2911 for router families and Catalyst3560 for switch families. Five requests were rejected:

| Family | Rejected default combination | Suggested regression |
| --- | --- | --- |
| `switch.trunk_native` | `interface_mode=access`, handler requires trunk | Run unmodified required examples through public generator |
| `switch.trunk_allowed` | Same incompatible mode default | Include operation-specific VLAN requirements |
| `switch.etherchannel` | Required examples omit conditionally necessary `access_vlan` and `group_access_vlan` | Supply a complete coherent example, or surface conditional missing fields |
| `router.interface.dot1q` | Default physical interface lacks subinterface suffix | Use an Ethernet subinterface example |
| `router.rip.network` | `10.0.0.0/24`, handler requires explicitly supplied classful major prefix | Use `/8`; retain rejection of inferred widening |

The existing switch example helper overrides mode and adds EtherChannel fields, hiding the catalog inconsistency. The router suite checks hand-authored examples rather than all registry defaults. Keep those useful scenario tests, but additionally validate the actual shipped defaults without test-only repair. EtherChannel currently yields an ambiguous plan with a warning naming the missing field instead of `MissingParameters`; expose conditional requirements consistently. The coordinator reports addressing the examples; verification remains with its final candidate.

## Reviewed invariants and remaining boundaries

- **Defaults and encodings:** generic network parsing rejects a bare address and trailing hyphen fields. Static routes accept exact supported structural encodings, reject host-bit destinations, unsupported reserved fields, zero/bad distances, and incomplete targets. Hyphen encodings are project fixture conventions, not Cisco CLI syntax or independently established private activity formats.
- **Masks and typed handlers:** contiguous subnet checks and explicit IPv4 network/host distinctions are enforced in the main typed paths; switch handlers additionally restrict their supported host mask range. Public `router::generate` and `cisco::generate` have differing validation layers, so regression tests should exercise the public facade used by the UI as well as module handlers. A supplemental probe found `router.interface.ipv4` accepts `127.0.0.1/8` on Gi0/0; the router host-address filter is less restrictive than the switch filter. Treat reserved and loopback address rejection as an additional follow-up; no IOS acceptance test was run.
- **Unique current proof:** comparison resets stale statuses, requires one current snapshot and one named device, rejects duplicate ports/configs in supported paths, and scopes route-absence evidence to the named device. Missing or opaque configuration stays Unverified. The new scalar validator requires unique device/snapshot proof and explicit relevant static port mode. Add integrated regressions for repeated alias mode headers, absent current config, and duplicate device names around new scalar checks, not only direct validator tests.
- **OSPF requirements:** no implicit process 1 or area 0 is added. Missing/conflicting evidence remains incomplete. Decimal/dotted area equality remains R4. Non-contiguous wildcard requests outside the supported prefix-based generator subset should stay unsupported with an explicit reason rather than being widened.
- **ACL and copying:** the saved-config parser retains ACL order. The batch builder uses stable ordering and preserves order among global ACL entries; the existing ordering test passes. Plans are deduplicated, scalar conflicts are omitted, VLAN definitions precede interface configuration, and saves are emitted last. R2/R3 show why individual and batch generation must share all prerequisite and identity checks. Clipboard delivery itself was not exercised.
- **Routes:** an independent script probe retained both a primary route via `192.0.2.1` and a same-prefix route via `192.0.2.2` at distance 20. The ECMP/floating regression passes on the newer candidate. These prove configured statements only, not next-hop reachability, route installation, load sharing, or failover. Cisco explains [floating route preference and distance 255 exclusion](https://www.cisco.com/c/en/us/support/docs/dial-access/floating-static-route/118263-technote-nexthop-00.html); an accepted configuration with distance 255 must not be presented as a working forwarding route.
- **Resource bounds:** XML input is capped at 64 MiB, one million nodes and depth 128; assessment expansion and matching have explicit budgets. Config parsing caps input at 4 MiB, 50,000 lines and 4096 bytes per line, rejects opaque multiline constructs, and now rejects repeated recognized mode identities. Comparison adds a checkpoint-times-config-text budget of 512 MiB in addition to the node-operation budget. These are source-reviewed bounds, not a worst-case latency or memory benchmark. Future tests should exercise the aggregate byte limit with a small-node, large-text snapshot, plus exact boundary and oversized-line cases, while proving stale results clear.
- **Prerequisite honesty and support labels:** registry metadata distinguishes implemented semantic checks and keeps Packet Tracer execution unverified. Explicit context parameters are caller assertions, not independently measured device state. Library examples cannot establish dependency readiness; R5 needs correction. Hardware documentation and successful offline generation must not become a VerifiedPacketTracer label.
