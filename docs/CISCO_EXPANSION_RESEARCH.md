# Cisco command expansion research

Researched 2026-10-23 against public Cisco command references and configuration guides; repository baseline inspected at `47fb1b3`. Original implementation analysis, with short CLI forms rather than copied manual passages. This document proposes work; it adds no command families and changes no compatibility claims.

## Evidence boundary

Coordinator implementation update: branch `feature/cisco-services-coverage` adds eight bounded workflows (DHCP relay, serial DCE clock, serial PPP, two CDP states and three OSPFv2 controls). The rows below retain the **47fb1b3 baseline** for comparison. These additions have synthetic generation tests and explicit checkpoint aliases, but no new semantic grading or actual Packet Tracer execution certification. Serial module/cable/peer inputs are explicit operator assertions; this build does not discover them. Standalone RIP, NTP, LLDP and VTP setters remain research opportunities.

The baseline has **46 registered families and zero Packet Tracer execution-certified families** (`CISCO_COMMAND_COVERAGE.md`). A template can generate commands from explicit inputs without having a reliable PKA assessment mapping. Cisco documentation establishes syntax and behavior on its named software/hardware, not the simulated feature inventory of PT. **Every row below remains uncertified in real PT execution.** No private PKA, exam, device session, or restrictive source was used.

Read-only code inspection found `router.rip.network` already emits an explicit version, `router.dhcp.exclude` already emits exclusions, and `switch.vlan` consumes VTP mode/version as prerequisites. These are not three wholly new families. `src/cisco/mapping.rs` has no dedicated mapping for these expansion properties; `src/commands.rs` has legacy explicit-value branches for `ripnetwork` and `dhcpexcludedaddress`, which do not establish reliable extraction of missing PKA context. OSPF network mapping exists, but does not establish router-ID, passive, or reference-bandwidth mappings.

## Practical research matrix

Modes are exact configuration contexts: **G** = global `(config)#`; **I** = selected interface `(config-if)#`; **R** = selected routing process `(config-router)#`. Enter R through G with `router rip` or `router ospf <process-id>`. All `show` commands are read-only privileged EXEC suggestions, not automatically executed. Source IDs resolve to software-specific Cisco URLs below. Proposed IDs are suggestions, not registered support.

## Implementation order and acceptance limits

Suggested first wave: explicit CDP booleans and DHCP relay, then OSPF process options and RIP passive. Extend evidence/mapping for existing RIP version and DHCP exclusion templates instead of increasing the family count for their existing behavior. Serial features wait for module/cable evidence; VTP mutation waits for database/revision context. Discovery inspection can supply observations but must not create desired configuration implicitly.

For each future implementation, require typed inputs, context-preserving generation and saved-config comparison, then separately establish a PKA mapping using unambiguous named assessment fields with missing/conflicting values left unresolved. Finally record PT version, exact device/image/module/interface inventory, initial configuration, accepted/rejected commands, saved running configuration and operational show output in a test-only lab. No mapping fixture, parser test, generated example, or real-hardware Cisco source can substitute for that execution evidence. This research performed no PT execution and makes no reliable new PKA mapping claim.
